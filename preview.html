Hover fill — shown large, always on
  • Seven blobs, seven timelines. Each colour is its own element with its own path and duration (9–15s), so they never collapse onto one point.
  • Proportional falloff. Each blob's edge is a radial ramp in its own percentages, so the softness is identical at 28px and at demo size — a fixed pixel blur would show disc arcs when magnified.
  • Transform-only motion. Continuous, compositor-cheap, and independent per blob.
  • Clipping frame. The mesh container is inset: 0 with overflow: hidden, over an opaque base, so no frame can expose bare menu surface.
  • Blobs wider than the strip. 60% of the width each, anchored at 7–94%, so every hue keeps its own patch while overlapping its neighbours.
  • Built in JS. content.js appends the mesh span and seven blob spans; the CSS owns everything visual.

At a real menu item's 28px height only a horizontal slice through the middle of this is visible.

I spent some time digging into why the incremental build regressed after we split the app into feature modules. The short version is that the module graph is fine, but every target re-emits the shared Design module's interface file, so downstream targets always look dirty to the build system.

Two options. We can stop re-emitting by pinning the interface output path per configuration, which is a two-line change but makes clean builds slightly slower. Or we can split Design into a tokens-only target that almost never changes and a components target that does — bigger change, but it fixes the underlying fan-out instead of hiding it.

I lean towards the second, since we will hit the same wall again when the iOS app lands. Happy to be talked out of it if someone has numbers.
